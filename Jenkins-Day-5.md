# Jenkins Day 5 – Jenkins Pipeline

## 1. Introduction to Jenkins Pipeline

A **Pipeline** is a sequence of steps or activities executed one after another to complete a process.

In DevOps, an application development and delivery process commonly includes:

1. Getting source code from a version control system.
2. Building or compiling the application.
3. Running automated tests.
4. Performing code quality checks.
5. Generating an artifact.
6. Deploying the application.

Jenkins Pipeline automates these activities instead of requiring us to execute every step manually.

### What is a Jenkins Pipeline?

A Jenkins Pipeline is a script written using a **Groovy-based Domain-Specific Language (DSL)**. It defines the sequence of execution steps that Jenkins should perform through automation, such as building an application, running tests, performing code quality checks, and deploying an application.

The pipeline's execution and final result depend on the stages and steps defined in the script.

For example:

- **Build:** Compile the application and generate build output.
- **Test:** Execute automated tests.
- **Code Quality Check:** Analyze the source code using tools such as SonarQube.
- **Deploy:** Deploy the application to the required environment.

### Important Terminology

| Term | Meaning |
|---|---|
| Groovy | Programming language used as the foundation for Jenkins Pipeline scripting. |
| DSL | Domain-Specific Language; provides instructions designed for a particular purpose. |
| Pipeline | Defines the complete automation workflow. |
| Stage | A logical section of the pipeline representing an activity. |
| Step | An individual instruction executed inside a stage. |
| Artifact | The output generated by the build process, such as a JAR or WAR file. |

**Remember:** Groovy provides the scripting foundation, Jenkins Pipeline DSL provides Jenkins-specific instructions, and Jenkins executes and coordinates the defined workflow.

## 2. Types of Jenkins Pipeline

There are two main types of Jenkins Pipeline:

1. Scripted Pipeline
2. Declarative Pipeline

### 2.1 Scripted Pipeline

- Scripted Pipeline uses Groovy scripting with a more flexible programming approach.
- It allows greater control over pipeline execution using Groovy programming constructs.
- It is useful when complex scripting logic is required.

### 2.2 Declarative Pipeline

- Declarative Pipeline follows a structured and predefined syntax.
- It is easier to read and organize for common CI/CD workflows.
- It uses predefined sections such as `pipeline`, `agent`, `stages`, `stage`, and `steps`.

Both types are supported by Jenkins. Declarative Pipeline is a useful starting point when learning to write structured Jenkins automation.

### Difference Between Scripted and Declarative Pipeline

| Scripted Pipeline | Declarative Pipeline |
|---|---|
| More flexible scripting approach. | Structured pipeline syntax. |
| Uses Groovy programming constructs more directly. | Uses predefined Pipeline DSL sections. |
| Suitable for complex custom logic. | Suitable for organized, readable CI/CD workflows. |
| Requires understanding of Groovy scripting. | Easier to understand when starting with Pipeline. |

## 3. Basic Declarative Pipeline Structure

A Declarative Pipeline starts with the `pipeline` block.

The basic structure is:

```groovy
pipeline {
    agent any

    stages {
        stage('Stage Name') {
            steps {
                // Instructions to execute
            }
        }
    }
}
```

### Understanding Each Section

**1. pipeline**

- It is the starting block of a Declarative Pipeline.
- The complete pipeline configuration is written inside it.

**2. agent**

- Defines where the pipeline or its stages should execute.
- Jenkins uses agents to execute build activities.

Example:

```groovy
agent any
```

This means Jenkins can execute the pipeline on any eligible available agent.

We can also specify a particular agent using its label:

```groovy
agent {
    label 'slave-one'
}
```

This instructs Jenkins to execute the pipeline on an agent matching the `slave-one` label.

**3. stages**

- A pipeline can contain multiple stages.
- Each stage represents a logical activity in the automation process.

Examples:

- Checkout
- Build
- Test
- Code Quality
- Artifact
- Deploy

**4. stage**

- Defines an individual stage inside the `stages` block.
- We can give each stage a meaningful name.

**5. steps**

- Contains the actual instructions that Jenkins must execute inside a stage.
- Examples include checking out source code, executing Maven commands, and running Linux commands.

### PASS Shortcut

A useful shortcut for remembering the basic Declarative Pipeline structure is **PASS**:

| Letter | Meaning |
|---|---|
| P | Pipeline |
| A | Agent |
| S | Stages |
| S | Steps |

Remember the order:

**Pipeline → Agent → Stages → Stage → Steps**

## 4. Creating the First Jenkins Pipeline

### Example 1: Print Hello World

Create a new Jenkins Pipeline job:

1. Open the Jenkins Dashboard.
2. Click **New Item**.
3. Enter the job name: `Netflix`.
4. Select **Pipeline**.
5. Click OK.
6. Scroll to the Pipeline script section.
7. Enter the following script.

```groovy
pipeline {
    agent any

    stages {
        stage('First Stage') {
            steps {
                echo 'Hello World'
            }
        }
    }
}
```

Save the job and click **Build Now**.

### Understanding the Execution

- Jenkins reads the pipeline script.
- `agent any` selects an eligible execution node.
- Jenkins enters the `First Stage`.
- The `echo` step prints `Hello World`.
- The build result is displayed in Jenkins.

**Important:** The `echo` instruction is a Jenkins Pipeline step. It prints a message in the build log.

## 5. Executing Linux Commands Through Jenkins Pipeline

We can execute Linux commands from a Jenkins Pipeline using the `sh` step.

The `sh` step executes shell commands on the node where the pipeline is running.

### Example 2: Create a File

```groovy
pipeline {
    agent any

    stages {
        stage('Create File') {
            steps {
                sh 'touch file1'
            }
        }
    }
}
```

When the pipeline executes:

1. Jenkins selects an eligible agent.
2. It enters the `Create File` stage.
3. The `sh` step executes the Linux `touch` command.
4. A file named `file1` is created in the current workspace directory.

We can verify the file by navigating to the workspace on the execution node.

Example:

```bash
cd /var/lib/jenkins/workspace/Netflix
ls -l
```

The actual workspace location depends on the Jenkins configuration and execution node.

### Example 3: Create Another File

```groovy
pipeline {
    agent any

    stages {
        stage('Create File') {
            steps {
                sh 'touch file2'
            }
        }
    }
}
```

After executing the pipeline, `file2` is created in the workspace.

### Example 4: Execute CPU Information Command

We can execute other Linux commands in the same way.

```groovy
pipeline {
    agent any

    stages {
        stage('System Information') {
            steps {
                sh 'lscpu'
            }
        }
    }
}
```

The `lscpu` command displays CPU architecture and processor information in the build logs.

### Important Understanding: Workspace

The Jenkins workspace is the working directory where Jenkins checks out source code and performs build activities.

For example:

```text
/var/lib/jenkins/workspace/Netflix/
```

The workspace can contain:

- Checked-out source code.
- Maven `pom.xml`.
- Build output.
- Files generated by pipeline commands.
- Other temporary build-related files.

**Important:** Workspace paths can differ between the controller and agents. A workspace is not permanent artifact storage. Important build outputs should be archived or stored in an appropriate artifact repository.

## 6. Single-Stage Pipeline

A pipeline containing only one stage is called a **Single-Stage Pipeline**.

Example:

```groovy
pipeline {
    agent any

    stages {
        stage('Create File') {
            steps {
                sh 'touch file1'
            }
        }
    }
}
```

Here:

- One pipeline is defined.
- One stage is created.
- One instruction is executed inside that stage.

This is a simple way to understand how the Pipeline structure works.

---

## 7. Multi-Stage Pipeline

A pipeline containing more than one stage is called a **Multi-Stage Pipeline**.

Each stage represents a separate activity in the automation workflow.

For example:

1. Checkout – Get source code.
2. Build – Compile the application.
3. Test – Execute tests.
4. Artifact – Generate the application package.

### Example: Multi-Stage Pipeline

```groovy
pipeline {
    agent any

    stages {
        stage('Stage 1') {
            steps {
                echo 'First Stage'
            }
        }

        stage('Stage 2') {
            steps {
                sh 'lscpu'
            }
        }

        stage('Stage 3') {
            steps {
                echo 'Third Stage'
            }
        }
    }
}
```

### How Does It Execute?

Jenkins executes the stages in their defined order.

- First, Stage 1 executes.
- After it completes successfully, Stage 2 executes.
- After Stage 2 completes successfully, Stage 3 executes.

If a stage fails, the normal sequential execution stops unless the pipeline defines error-handling behavior.

### Why Use Multiple Stages?

Multiple stages help us:

- Separate different activities.
- Understand where a pipeline failed.
- View the progress of individual activities.
- Troubleshoot build problems more easily.
- Organize complex CI/CD workflows.

In practical CI/CD workflows, multi-stage pipelines are commonly useful because they provide better visibility into the execution process.

## 8. Integrating GitHub with Jenkins Pipeline

In a Freestyle job, we configure Git through the Source Code Management section in the Jenkins UI.

In a Pipeline job, we define the Git checkout operation using Pipeline syntax.

### Pipeline Syntax Generator

When we do not know the syntax for a particular Jenkins operation, we can use the **Pipeline Syntax** option.

Steps:

1. Open the Pipeline job configuration.
2. Find the Pipeline Syntax option.
3. Open the Snippet Generator.
4. Select the Git checkout operation.
5. Enter the repository URL.
6. Select the required branch.
7. Configure credentials if required.
8. Click Generate Pipeline Script.
9. Copy the generated script into the pipeline.

For a public GitHub repository, credentials are generally not required for read access. A private repository requires appropriate credentials.

### Example: Git Checkout

```groovy
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/OWNER/REPOSITORY.git'
            }
        }
    }
}
```

Replace the repository URL with the actual GitHub repository URL.

**Important:** The Git checkout operation downloads the repository source code into the workspace of the node executing that stage.

The Pipeline Syntax Generator is useful because it helps generate the correct syntax for Jenkins operations and plugins.

For advanced checkout requirements, Jenkins also provides the `checkout scmGit` syntax.

## 9. Integrating Maven with Jenkins Pipeline

After retrieving the source code from GitHub, the next activity is to build the application.

Maven is a build automation tool commonly used for Java projects.

In Jenkins Pipeline, we can execute Maven commands through the `sh` step.

### Maven Commands Used

| Command | Purpose |
|---|---|
| `mvn compile` | Compiles the application source code. |
| `mvn test` | Executes the configured tests after the required earlier lifecycle phases. |
| `mvn clean package` | Cleans previous build output and executes the Maven lifecycle through the package phase. |

### Example: Complete Multi-Stage Maven Pipeline

The following example follows the demonstrated execution sequence:

```groovy
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/OWNER/REPOSITORY.git'
            }
        }

        stage('Build') {
            steps {
                sh 'mvn compile'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }

        stage('Artifact') {
            steps {
                sh 'mvn clean package'
            }
        }
    }
}
```

### Understanding the Execution

**Stage 1 – Checkout**

- Jenkins connects to the Git repository.
- It retrieves the source code.
- The source code is placed in the Jenkins workspace.

**Stage 2 – Build**

```bash
mvn compile
```

- Maven compiles the Java source code.
- Compilation errors can cause the stage to fail.

**Stage 3 – Test**

```bash
mvn test
```

- Maven executes the configured tests.
- If tests fail, the pipeline normally stops before reaching the next stage.

**Stage 4 – Artifact**

```bash
mvn clean package
```

- `clean` removes the previous build output.
- `package` executes the Maven lifecycle through the package phase.
- Maven generates the configured package, such as a JAR or WAR file.

The generated artifact is generally available inside the Maven `target` directory.

### Important Maven Execution Detail

The above pipeline demonstrates the individual commands used in the session. However, these commands repeat some work.

For example:

- `mvn test` already runs the earlier required lifecycle phases, including compilation.
- `mvn clean package` also runs the required phases through packaging, including compilation and tests.

Therefore, a normal Maven build may use:

```bash
mvn clean package
```

This single command performs the required build and test lifecycle activities before generating the package.

The separate stages are still useful when we want to demonstrate or organize individual activities, but we should understand that repeating Maven lifecycle commands can increase build time.

## 10. Pipeline as Code

**Pipeline as Code** means defining the CI/CD workflow in a script and maintaining that definition as code rather than relying only on manual Jenkins UI configuration.

A Jenkins Pipeline script can contain multiple activities and organize them into one or more stages.

### Example 1: Multiple Activities in a Single Stage

```groovy
pipeline {
    agent any

    stages {
        stage('Build and Test') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/OWNER/REPOSITORY.git'

                sh 'mvn compile'
                sh 'mvn test'
                sh 'mvn package'
            }
        }
    }
}
```

Here:

- The pipeline has one stage.
- The stage contains multiple steps.
- Jenkins executes those steps in order.

### Example 2: Pipeline as Code with Multiple Stages

```groovy
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/OWNER/REPOSITORY.git'
            }
        }

        stage('Build') {
            steps {
                sh 'mvn compile'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }

        stage('Package') {
            steps {
                sh 'mvn package'
            }
        }
    }
}
```

This is also Pipeline as Code.

### Important Difference

Pipeline as Code does not mean that all activities must be written inside a single stage.

We can write:

- Multiple steps inside one stage.
- Multiple stages inside one pipeline.
- Multiple shell commands inside one shell step.

All these approaches can be part of a Pipeline as Code implementation.

### Why Is Pipeline as Code Useful?

A pipeline can be maintained in a `Jenkinsfile` inside the application's Git repository.

For example:

```text
Java-Application/
│
├── src/
├── pom.xml
└── Jenkinsfile
```

Benefits:

- Pipeline configuration can be version-controlled.
- Changes can be tracked through Git.
- Pipeline definitions can be reviewed.
- The same pipeline can be maintained alongside application source code.
- Teams can collaborate on CI/CD automation.

**Important distinction:** Writing multiple commands inside a stage is not, by itself, the definition of Pipeline as Code. The key idea is maintaining the pipeline definition as code, commonly in a version-controlled `Jenkinsfile`.

## 11. Executing Multiple Commands Using a Single Shell Step

In Jenkins Pipeline, we can execute multiple Linux commands using one `sh` step.

Instead of writing separate `sh` steps for every command, we can use a multiline shell script.

### Example: Separate Shell Steps

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                sh 'mvn compile'
                sh 'mvn test'
                sh 'mvn package'
            }
        }
    }
}
```

Here, Jenkins invokes three separate shell steps.

### Example: Multiple Commands in One Shell Step

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                sh '''
                    mvn compile
                    mvn test
                    mvn package
                '''
            }
        }
    }
}
```

Here:

- Only one `sh` step is defined.
- The shell script contains multiple commands.
- Commands execute sequentially within that shell step.
- Jenkins displays the output in the build logs.

### Difference Between the Two Approaches

| Separate Shell Steps | Multiline Shell Step |
|---|---|
| Each command uses its own `sh` step. | Multiple commands are grouped in one `sh` step. |
| Jenkins invokes separate shell steps. | Jenkins invokes one shell step. |
| Each shell step has its own execution result. | Commands run within the same shell execution. |

**Remember:** A shell step and a Jenkins stage are different things. Multiple shell commands inside one `sh` block do not create multiple Jenkins stages.

## 12. Pipeline Execution on Jenkins Agents

In the previous Jenkins session, we learned about the Controller and Agent architecture.

A Jenkins Controller manages the jobs and coordinates execution. Agents provide the environments where build tasks can run.

A Pipeline can execute on an eligible agent using the `agent` directive.

### Using Any Available Agent

```groovy
pipeline {
    agent any

    stages {
        stage('Build') {
            steps {
                echo 'Executing Pipeline'
            }
        }
    }
}
```

`agent any` allows Jenkins to select any eligible available node.

It does not guarantee that the build will execute on a particular agent.

### Executing on a Specific Agent

Suppose we have an agent named `slave-one`.

In the agent configuration, a label has been assigned:

```text
slave-one
```

We can specify that label in the Pipeline:

```groovy
pipeline {
    agent {
        label 'slave-one'
    }

    stages {
        stage('Build') {
            steps {
                echo 'Executing on slave-one'
            }
        }
    }
}
```

Now Jenkins selects an available agent matching the specified label.

### Difference Between Freestyle and Pipeline Agent Configuration

| Freestyle Job | Pipeline Job |
|---|---|
| Configure the execution node using the job's UI configuration. | Specify the execution node through the `agent` directive. |
| Restrict where the project can run using the available node configuration. | Use `agent any` or a specific agent label. |

The important point is that the pipeline script itself defines where the workflow should execute.

## 13. Agent Troubleshooting – Java Compatibility

Consider this scenario:

- The Jenkins Controller is running.
- The agent server is running.
- Jenkins is unable to establish or maintain the agent connection.
- The agent appears offline.

One important area to investigate is the Java runtime used by the Jenkins agent process.

### Java 21 Requirement

For the Jenkins version discussed in this learning material, use Java 21 as the required baseline for the Jenkins Controller and Agent JVMs.

Check the Java version on the agent:

```bash
java -version
```

The agent JVM must meet the Java requirements of the installed Jenkins release.

### Troubleshooting Steps

1. Check whether the agent server is running.
2. Check whether the agent is online in Jenkins.
3. Connect to the agent server.
4. Check the installed Java version.
5. Verify that Java 21 is available and configured correctly.
6. Check the agent connection and launch logs.
7. Reconnect or relaunch the agent.
8. Confirm that Jenkins displays the agent as online.

The Java runtime used to run the Jenkins agent process is separate from the JDK that an application may require for compilation.

If the Java application uses a different JDK, configure the appropriate build toolchain separately.

**Important:** Do not change the system's default Java version blindly. First check the installed versions and determine which Java runtime the Jenkins agent service or launch process actually uses.

## 14. Verifying Pipeline Execution on an Agent

After the agent becomes online, execute the pipeline using its assigned label.

For example:

```groovy
pipeline {
    agent {
        label 'slave-one'
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/OWNER/REPOSITORY.git'
            }
        }

        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }
    }
}
```

### How to Verify the Execution

1. Confirm that `slave-one` is online.
2. Configure the pipeline to use the `slave-one` label.
3. Save the pipeline.
4. Click **Build Now**.
5. Open the build logs.
6. Check the execution details and workspace path.
7. Connect to the agent server and inspect the workspace.

Example workspace path from the demonstration:

```text
/tmp/workspace/Netflix-pipeline-one
```

This is an example path, not a universal Jenkins workspace location.

The actual path depends on the agent's remote root directory, Jenkins configuration, and any custom workspace settings.

You can inspect the directory using:

```bash
cd /tmp/workspace/Netflix-pipeline-one
ls -l
```

You may find files such as:

```text
pom.xml
src/
target/
```

This confirms that Jenkins checked out the project and executed the build activities on the selected agent.

### What Did We Achieve?

Previously, we learned how to distribute Freestyle jobs across Jenkins agents.

Now we can do the same with Pipeline jobs.

The important difference is:

- Freestyle uses its job configuration to select the execution node.
- Pipeline uses the `agent` directive and label to select the execution node.

### Final Understanding

A Jenkins Pipeline allows us to define the complete application build and delivery workflow using code.

Instead of manually retrieving source code, executing Maven commands, testing applications, and generating artifacts, we define these activities in a Pipeline script.

Jenkins then executes the defined steps in sequence, provides stage-level execution visibility, and allows us to run the workflow on selected agents.

This makes CI/CD automation more repeatable, organized, maintainable, and easier to troubleshoot.
